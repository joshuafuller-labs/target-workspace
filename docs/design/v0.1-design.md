# Target Workspace — Design v0.1

Working design. Subject to revision after personas, journeys, and JTBD are settled.

## TAK backend strategy

Make the publisher pluggable; invest in **TAK Server (official)** as the primary target.

- **TAK Server** is what DoD/IC/LE production environments run. TLS, federation, Marti REST API, mission persistence. Primary production target.
- **Raw CoT (TCP/UDP/SSL emitter)** is the lowest-common-denominator fallback — pushes directly to an ATAK EUD or any CoT consumer with no server in between.

Because Publisher is an adapter (symmetric to Source), this is not a one-way door. Ship TAK Server first, raw CoT as fallback. Customers can add their own.

## Core principles

1. **Everything that varies between deployments is data, not code.** Board columns, promotion thresholds, normalization maps, source configs, publisher configs.
2. **OpenAPI is the public contract surface** — both inbound and outbound.
3. **Adapters, not integrations.** Sources and Publishers implement a small interface; the core knows nothing about specific vendors or TAK flavors.
4. **Provenance is non-negotiable.** Every Target carries its full chain — source, raw payload reference, confidence, who promoted through each gate.
5. **Human-in-the-loop is a policy, not an architecture.** Same code path handles autonomous and gated flows; the difference is the `PromotionPolicy` attached.

## Architecture (logical)

```
Source Adapters (plugins, OpenAPI contract)
  manual UI | HTTP-pull | webhook | CoT-in | MQTT | Kafka | ...
                       |
                       v
            Ingest API (POST /v1/detections)
                       |
                       v

                       |

  (Boards w/ user-defined columns | PromotionPolicy per source

                       |

   Publisher Adapters (plugins, symmetric to Sources)
   TAK Server | raw CoT | Mission pkg | webhook-out

Kanban UI <-> REST/WebSocket <-> Workflow Engine <-> Audit/Replay store
```

## Key abstractions

### `Target` — canonical entity (CoT-compatible superset)

- identity: `id`, `name`, `cot_type` (e.g., `a-h-G-U-C-F`), `category`
- geometry: `lat`, `lon`, `hae`, `ce`, `le`, `time`, `stale`
- workspace context: `workspace_id`, `board_id`, `column_id`
- AI/source signal: `confidence` (0..1), `provenance[]` (source_id, payload_ref, timestamp)
- handling: `classification`, `caveats[]` (design for U/CUI/higher even if MVP is U-only)
- workflow: `assignee`, `watchers`, `state_history[]`
- payload: `attachments[]` (imagery, bbox, links), `custom_fields{}`

### `Board` — workspace + workflow definition

- `columns[]`: ordered `{id, name, color, wip_limit?, entry_actions[], exit_actions[]}` — fully user-defined
- `transitions{}`: allowed column-to-column moves (or `*` for free movement)
- `views[]`: saved filters

### `Source` — input adapter config

- `type`: `manual | http_pull | webhook | cot_in | mqtt | kafka | custom`
- `adapter_config`: connection/auth/poll interval
- `normalization_map`: jq/jmespath expression mapping source schema -> `Target`
- `promotion_policy_id`: which policy applies to detections from this source

### `PromotionPolicy` — the autonomy spectrum, as a row

- `mode`: `gated | conditional | autonomous`
- `min_confidence`: threshold for `conditional`
- `required_stages[]`: columns the target MUST pass through (e.g., must hit "Approved")
- `approval_roles[]`: who can promote past each gate
- `auto_publish_column_id`: which column triggers Publisher dispatch
- `on_low_confidence`: `route_to_column_id` (e.g., low-conf CV detections -> "Triage")

This single object expresses the full spectrum: pure-human-gate, conditional auto-promote, or full autopublish. Per source, per board, overridable.

### `Publisher` — output adapter config

- `type`: `tak_server | raw_cot | mission_pkg | webhook`
- `endpoint`, `auth`, `cert_bundle_ref`
- `filter`: which targets trigger (board/column/tag predicates)
- `cot_template`: render rules `Target -> CoT XML` (also data, jinja-style)

## Modularity story ("even the kanban bins")

| Concern | Where it lives | Customer can change without code? |
|---|---|---|
| Column names / order / colors / WIP | `Board.columns[]` in DB | Yes, via admin UI |
| Which columns require approval | `PromotionPolicy.required_stages` | Yes |
| Auto-promote thresholds | `PromotionPolicy.min_confidence` | Yes, per source |
| Source schema -> Target mapping | `Source.normalization_map` (jq) | Yes |
| Target -> CoT XML rendering | `Publisher.cot_template` | Yes |
| New OSINT vendor | New `Source` plugin | Code, but isolated |
| New TAK flavor | New `Publisher` plugin | Code, but isolated |

Plugin loading mechanism is an open question (in-process entry-points vs sandboxed runtime like WASM). Decision deferred until tech stack is chosen.

## The autonomy spectrum, made concrete

```yaml
# Source: high-trust validated OSINT feed
promotion_policy:
  mode: autonomous
  auto_publish_column_id: published

# Source: CV/ATR inference pipeline
promotion_policy:
  mode: conditional
  min_confidence: 0.85
  on_low_confidence:
    route_to_column_id: triage
  required_stages: [approved]   # high-conf still hits approval before publish
  auto_publish_column_id: published

# Source: open-web OSINT scraper
promotion_policy:
  mode: gated
  required_stages: [triage, validated, approved]
  approval_roles: [analyst, supervisor]
```

Same engine, same code path, three behaviors. No branching logic in the workflow engine — it reads the policy.

## Cross-cutting concerns

- **AuthN/Z**: OIDC + RBAC; design for ABAC (classification-tagged targets) from day one
- **Audit**: append-only event log of every Target state change with actor; replayable
- **Real-time UI**: WebSocket fanout from the workflow engine; kanban drag-drop = state transition event
- **Geo**: needs a spatial-aware datastore and tile rendering for the map pane
- **Dedupe**: spatial + temporal proximity + name similarity; tunable per workspace
- **Deployment**: containerized, must run airgapped (DoD reality)

## Supply-chain posture (greenfield bar)

SHA-pinned actions, Dependabot, CodeQL, SBOM (CycloneDX), cosign-signed images, pre-commit gating, conventional commits, TDD from commit 1. Threat model document before code. Non-negotiable for anything handling cleared workflows.

## Proposed MVP scope (when implementation starts)

1. Core: `Target`, `Board` with configurable columns, `PromotionPolicy`, audit log
2. One Source adapter: **manual entry** (UI form) — proves the loop without external deps
3. One Publisher adapter: **TAK Server** via Marti REST — proves the production path
4. One more Source: **webhook ingest** with jq normalization — proves the plugin pattern
5. Kanban UI with map pane, drag-drop, real-time updates
6. Confidence-conditional policy working end-to-end with a fake "CV detection" webhook

Everything else (more sources, raw CoT, mission packages, MQTT/Kafka, sandboxed plugins) is post-MVP and slots into the same shapes.

## Deferred / open questions

- **Naming.** Product name? "Target Workspace" is a working title.
- **Tech stack (frontend, backend, datastore, event bus).** Deliberately deferred — to be decided in a dedicated stack-selection conversation after personas and stories sharpen the constraints.
- **Open core vs closed source.** Plugin SDK published, core paid? Or all closed?
- **Multi-tenant vs single-tenant deploys.** Affects datastore design heavily.
- **Classification ceiling for v1.** U-only is simpler; CUI changes a lot. SECRET+ later.
- **Plugin sandboxing model.** In-process entry-points vs WASM (extism) vs subprocess. Tied to stack decision.
